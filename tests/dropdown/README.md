# 第二階段第 3 項：下拉選單共用能力測試

## 目的

建立可由不同使用位置獨立組裝使用、獨立測試、移除及替換的下拉選單共用能力。共用的是互動能力與必要介面，不共用選項內容、開合狀態或選取狀態。

## 已確認的架構依據

依《UI模組架構規劃書》第五版：

- 通用框架能力包含下拉選單，各能力各自獨立，依需求選用。
- 下拉選單採共用單元實作，各區域依需求獨立組裝使用，不重複建立相同功能的實作。
- 中間區的需求主題與右側區的標頭已確認使用下拉選單。
- 各使用位置保有自身的內容與操作狀態。
- 單元可獨立建置、使用、測試、替換及移除；組合不等於融合。
- 採用 Web Components，不使用前端框架；跨單元協作透過明確介面。

## 能力邊界與必要介面

`src/capabilities/dropdown.js` 提供：

- `bindDropdown({ trigger, menu, getExpanded, onExpandedChange, onSelect })`
  - 對呼叫端提供的原生按鈕綁定點擊開合操作。
  - 從 `getExpanded` 讀取該使用位置自己的開合狀態。
  - 透過 `onExpandedChange(nextExpanded)` 通知呼叫端；由呼叫端更新自己的狀態及選單顯示。
  - 對呼叫端提供的選單根節點使用事件委派；選項以 `data-dropdown-option` 提供值，透過 `onSelect(value, optionElement)` 交回呼叫端。
  - 回傳解除函式，移除本次連接建立的事件監聽，可獨立移除及替換。
- `syncDropdownState(trigger, expanded)`
  - 只同步觸發按鈕的 `aria-expanded` 無障礙狀態。

能力不保存開合或選取狀態、不建立全域選單資料、不建立使用位置註冊表、不管理選項內容、不決定選取後如何更新內容，也不替使用位置控制選單顯示。每個使用位置自行提供 trigger、menu、狀態讀取函式及回呼。選項內容與狀態由使用位置持有。

## 靜態檢查

- 能力模組只提供互動連接與無障礙狀態同步。
- 不存在全域選單資料、集中式選單狀態、使用位置註冊表或跨位置管理。
- 能力不建立、改寫、隱藏或移除呼叫端的選項內容。
- 狀態只透過呼叫端 getter/callback 讀取與更新。
- 選項值由呼叫端標記並由回呼接收。
- 連接回傳清理函式，可移除觸發及選項事件監聽。
- 測試頁直接載入能力模組，不載入 `src/main.js`。
- 測試頁含兩個各自提供不同選項內容及狀態的使用位置。
- 測試程式另與既有共用外觀、開合能力及基本單元組合檢查。
- 靜態檢查不等於瀏覽器實測。

## GitHub Pages 瀏覽器實測

公開測試頁：

`https://skyeden08.github.io/zizai-ui-framework/tests/dropdown/`

瀏覽器實測項目：

1. 頁面可正常開啟，測試模組及 CSS Variables 資源載入成功。
2. 測試結果由 `test-runner.js` 動態產生，不是預先寫入的結果文字。
3. 兩個以上使用位置各自保有不同選項內容、開合狀態及選取狀態；操作其中一處不改變另一處。
4. 選項值分別回到各自使用位置，由使用位置自行更新選取狀態及內容。
5. 與共用外觀及既有開合能力組合使用，互不干擾。
6. 與既有基本單元並存，不影響其載入及呈現。
7. 移除單一連接後，該位置的觸發及選項事件不再呼叫舊回呼；替換新連接後僅新回呼接收事件。
8. 檢查選項內容仍由使用位置持有，能力不集中管理或改寫內容與狀態。
